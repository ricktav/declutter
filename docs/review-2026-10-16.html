1. What HomeBase is, as the code tells it

A single-user home-inventory system for several houses. The core loop is register all, act later: Snap a photo or note into the inbox, Sort it (what is it, is it right, where is it), Act (keep, sell, donate, toss, later), Gone. Around that core, lenses add a field of work on the same Things: the Computer lab (device roles, backups, storage volumes, services, VMs, containers), Energy (meters, tariffs, monthly kWh), and a Spatial twin (LiDAR and GeoJSON room scans, 2D/3D plans, snap to wall, photo cameras). A third ring holds personal-knowledge tools: Ideas, Tasks with timers, a generated Wiki, an Ask-AI chat, a Galaxy bubble view, a Systems mind map and an Activity log.

Four clients share one tRPC API and one MySQL database: the desktop Workbench (/, 16 routes), the phone-first Flow (/flow/, 4 tabs), a native iOS app (7.9k lines of Swift), and the Computer Lab adapter. Collectors (Telegram bot, storage, services, energy) write through the same API. 339 commits landed between 2026-09-27 and 2026-10-15, most of them by agent sessions working in parallel; AGENTS.md freezes the contracts those clients depend on.

2. Diagnosis

What already serves "minimal start"

  • Flow's Snap tab asks nothing (src/flow/SnapTab.tsx); Sort and Act are one card at a time with skip; "Later" returns after seven days. This is the right loop.
  • Focus (src/pages/Focus.tsx) is room-first: numbered frames on a room photo, a thin sheet with name, topic, Place, decision. Temporary names like "Frame 3" are allowed.
  • Nav entries for Ideas and Tasks appear only when there is data (Layout.tsx:206-217); heavy pages are lazy-loaded (App.tsx:20-25).
  • rooms.ensure creates a room on the fly; x-house-id scopes every list; the API works without an LLM configured.
  • The API is transactional where it matters (items.create, inbox.acceptMany, scans), with an append-only event log and a good test seam.

What fights it

  1. Three "simple" front doors, no single home. Workbench Simple mode, Workbench Focus, Flow and the iOS app all implement a thin loop. Simple mode is only a nav filter plus a redirect to /focus (Layout.tsx:155-223); the Dashboard stays an admin page (house dialogs, topic creation, PDOK parcel lookup: Dashboard.tsx, 708 lines).
  2. The rules for "what needs me" live in three places and already differ. needsCheck / isUnplaced / needsDecision with LATER_DAYS = 7 exist in src/flow/data.ts:23-36 and ios/…/FlowLogic.swift:6-36; Focus has its own isUnhandledItem (Focus.tsx:56-58) that ignores the seven-day rule. The Dashboard counts a fourth way. Every new client copies the rules again.
  3. A Thing cannot exist without a Topic and a fresh database cannot make a Thing at all. items.areaId is notNull; Focus refuses to admit a frame without a topic (Focus.tsx:252); an empty database greets you with "run npx tsx db/seed.ts" (Dashboard.tsx:654-661) and a house must exist before a room can.
  4. Lenses and views are always on. Galaxy, Systems, Storage, Wiki, Activity, Meterkast↗ and Flow↗ sit in the sidebar of every install; A/B provider compare is a button on every inbox card (Inbox.tsx:674-692); a 5k-line collector library ships in api/lib; @huggingface/transformers (ONNX runtime) is a production dependency for localDetector.ts, which only a script imports.
  5. Monoliths. ItemDetail.tsx 1548 lines, Annotate.tsx 1371, Inbox.tsx 1323, RoomPlan.tsx 1286, api/routers/inbox.ts 1166, Systems.tsx 987. ItemDetail shows every section to every Thing; a teapot gets Relations, Tasks, Linked ideas, sub-objects and History whether or not any exist.
  6. Duplication. DECISIONS is defined twice (Focus.tsx:36, flow/data.ts:13), AREA_ICONS four times (Layout, Dashboard, Galaxy, lib/areaStyle.ts), nameScore twice (items.ts:18, inbox.ts:50), object detection twice (pins.detect, inbox.detectObjects), cutout creation three times (inbox.fileObject, inbox.acceptMany, photos.createCutout). 98 hard-coded colour literals (#d2ff00, #282c20, #3C5D41…) in 21 files instead of theme tokens. Lens fields are declared in src/flow/lenses.ts and in areas.attributeDefs (db/seed.ts).
  7. State that should be shared is per device. Depth (workbenchMode), the Flow lens, the snap Place (flow.snapPlace), skipped cards, hide-handled and topic favourites all live in localStorage, so a phone and a desktop disagree, and the iOS app cannot see them.
  8. Small API hygiene. 17 throw new Error(...) in routers (500s instead of 4xx), e.g. items.setDecision (items.ts:509) and inbox.triage (inbox.ts:365); items.search loads every item and filters in JS (items.ts:880-888); triage sends up to 200 item names from all houses in every prompt (inbox.ts:118-125); no foreign keys in the schema (integrity lives in deleteItemTx); items.create fires a background LLM call after every human create (items.ts:275-329).

3. The shape of the proposal

One app, three depths, one queue. Keep the data model (it is sound after the rooms and photos consolidations). Keep Flow and the iOS app as they are until the shared pieces exist. Then:

  • Depth replaces Simple/Advanced: Quick shows only the five product words; Standard adds kinds, attributes, documents; Detail adds lenses, plans and views. Same screens at every depth; sections appear, nothing moves.
  • One server-side work queue (items.queue) defines "to sort / to check / to place / to decide" once, for every client.
  • Lenses and views become switches stored on the server, off by default on a fresh install, and modules in the code (fields, queue rules, Thing sections, nav) rather than pages that know about each other.
  • A Thing needs nothing but a photo or a name to exist; the Sort queue asks for the rest.

The mockup shows what that looks like on a phone and on a desktop. The proposals below are the steps; they are independent unless a dependency is named.

A. Start minimal

A1First run creates a house and a default kind; no seed scriptSAPIWorkbench
Seen

An empty database shows "No topics yet — run npx tsx db/seed.ts" (Dashboard.tsx:654-661); a room cannot be made without a house (rooms.ensure requires one); the seed creates seven topics with a computers schema most users never need.

Proposal

On boot (or on the first houses.list / areas.list call) the API creates house "Home" and topic "Things" when both tables are empty, and marks that in settings. The Workbench shows a three-step first-run card instead of the seed hint: name your house → optional address → snap your first photo. The seed script stays for the computer-lab schema, run on demand from Settings (D2).

Why

Minute one becomes a snap, not a terminal.

A2A Thing does not need a Topic to existSAPIcontract+
Seen

items.areaId is notNull (db/schema.ts:64); items.create and inbox.acceptMany require areaId; Focus says "Pick a topic before admitting this frame." (Focus.tsx:252). Flow quietly defaults to the first topic (SortTab.tsx:350), which is a different answer to the same question.

Proposal

No schema change: the server keeps a default topic per install (the "Things" topic from A1, settings.defaultAreaId) and uses it when areaId is omitted in items.create and acceptMany items. Clients drop the required-topic validation; a Thing on the default topic appears in the Sort queue as "needs a kind" only at Standard depth (C1). Making the column nullable is the cleaner long-term answer but needs a migration and every client; not now.

Why

Topic is a Standard-depth concept. Quick depth has Thing, Place, Photo, Decision.

C. One definition of the work queue, and small API fixes

C1items.queue: the server says what needs attentionMAPIcontract+later Flow/iOS
Seen

Flow (src/flow/data.ts:23-36, queue.ts), iOS (FlowLogic.swift:6-36) and Focus (Focus.tsx:56-58) each define needs-check / unplaced / needs-decision. Focus omits the seven-day "Later" return; the Dashboard counts pending captures only. The lab's "needs role" and "backup missing" rules are in src/flow/lenses.ts and nowhere on the server.

Proposal

items.queue({ houseId?, roomId?, lens? }) → { toSort: captureIds, toCheck: itemIds, toPlace: itemIds, toDecide: itemIds, toName: itemIds, lens: { needsRole, needsBackup } , counts }, computed in api/lib/queue.ts with LATER_DAYS as one constant (later a setting). Workbench (Today, Places, Things filters) uses it first; Flow and iOS can switch when their owners choose, their local rules keep working meanwhile. Unit-tested once, on the server.

Why

The whole product is "what still needs me"; that question should have one answer.

C2Server-side search with a limitSAPI
Seen

items.search selects every active item and filters by name.includes(q) in JS, then slices 10 (items.ts:875-889); Flow's Find searches attribute values client-side over the full items.listAll (FindTab.tsx:18-43).

Proposal

WHERE name LIKE ? OR JSON_SEARCH(attributes, 'one', ?) IS NOT NULL LIMIT 20, scoped to the session house, plus an optional fields flag. Small now; it keeps the phone from downloading the inventory to answer "where is the kettle".

C3Optional limit/offset on the big listsSAPIcontract+
Seen

items.listAll, photos.listAll and rooms.list return everything; inbox.list caps at 200 silently (inbox.ts:258). Flow loads items.listAll twice (house and all houses, archived included; flow/context.tsx:368-371).

Proposal

Add optional limit and offset (default: unchanged, everything) and a total in the response only when limit is passed. No client has to change; the Things list and Photos page can page when the inventory passes a few thousand rows.

C4One object-detection and one cutout functionMAPI
Seen

pins.detect (pins.ts) and inbox.detectObjects (inbox.ts:461-582) build nearly the same prompt with reference photos and name matching. Cutout creation (crop, putFile, photos row, event, ensurePinForCutout) is written out in inbox.fileObject, inbox.acceptMany and photos.createCutout.

Proposal

api/lib/detect.ts (detectObjectsInPhoto(bytes, { referenceItems })) called by both procedures, and api/lib/cutouts.ts (createCutoutTx(tx, …)) called by all three. Behaviour identical; the three tests that cover them stay green.

C5Scope AI context to the session houseSAPI
Seen

buildTriageContent lists up to 200 active items from every house in each triage prompt (inbox.ts:118-125); detectObjects and pins.detect do the same (inbox.ts:494, pins.ts:250). resolveSuggestion then has to discard matches from other houses (inbox.ts:170-175).

Proposal

Filter the candidate list by ctx.houseId (and the capture's houseId), order by the room of the capture's location Photo first, cap at 200. Fewer tokens, fewer wrong matches, no contract change.

C6TRPCError codes instead of throw new ErrorSAPI
Seen

17 plain throws in routers, e.g. items.setDecision and patchAttributes ("Item not found.", items.ts:509, 540), inbox.triage (inbox.ts:365), areas.update slug clash (areas.ts:100), houses.reassign. They surface as 500 INTERNAL_SERVER_ERROR; clients cannot tell "not found" from "crashed".

Proposal

Replace with NOT_FOUND / BAD_REQUEST / CONFLICT. One sitting; the messages stay.

C7Background link suggestions become opt-inSAPI
Seen

Every human items.create inserts name-similarity relations synchronously and then fires a fire-and-forget LLM call that inserts more relations after the response (items.ts:238-329). Importers pass suggestLinks: false; people cannot.

Proposal

Default suggestLinks from the AI module switch (D2) instead of true, and run the LLM part through the same small job queue as G1 so two creates do not race two LLM calls.

4. A sequence that keeps every client working

Step 1 — no schema change, no contract break

C6, C5, E2, E1, E7, D4, D3, G2, H1, H2, A2 (server default), B1 (depth, Workbench only), B4, F3. Each is one session; the live site, Flow, iOS and the lab adapter do not notice.

5. Not proposed

  • Rewriting Flow or folding the iOS app into a web view. Both work and have owners; the proposals give them shared server rules to adopt at their own pace.
  • Replacing MySQL with SQLite "for an easy start". The SQL is MySQL-shaped and the live data is MySQL; A4's compose file is the cheaper answer.
  • Removing any lens. The Systems, Energy and Spatial work is real and tested; the proposals make it optional and separable, not smaller.
  • Changing the AGENTS.md attribute keys, procedure names or inputs. Every proposal that touches a contract adds an optional field.
