# Rules for agents in this repo

Read this before you change code. These rules apply to every agent (Kimi, Claude sessions, others) and to Rick's own scripts. Rick decides when a rule changes.

## 1. Who owns what

| Area | Files | Owner |
| --- | --- | --- |
| Flow front end | `flow/`, `src/flow/` | Claude session "declutter-flow" |
| Workbench front end | `index.html`, `src/pages/`, `src/components/`, `src/context/` | Rick, or the session Rick assigns |
| API and database | `api/`, `db/` | Shared: follow sections 2, 3 and 4 |

- Do not edit `flow/` or `src/flow/`. If your change needs a Flow change, stop and tell Rick.
- If `npm run check` shows errors only under `src/flow/`, your change broke a Flow contract. Do not fix Flow yourself. Tell Rick.
- Do not commit files that another session made (for example its plans in `docs/`).
- On 2026-10-03 one session (finalize plan) worked on every area; the ownership above applies again to new work.

It upserts by (itemId, month) in one transaction, never deletes, and writes no item event (31 meters report nightly; these are measurements, not edits). Reads: `energy.overview` (last 12 complete months; scoped like storage.overview), `energy.forItem` (a plug, or an item a plug powers; `plug: null` for anything else). Writes by Rick: `energy.setTariff` (logs an event; optional `netMetering`, default true). Net metering (saldering, Energiek): a tariff row's `netMetering` flag decides per month; over the window's netMetering months import and export net as a whole (saldering is yearly), the netted kWh cost the average import price, terugleverkosten (`feedInCost`) apply to all exported kWh and terugleververgoeding (`feedIn`) only to the surplus above import; months without netMetering pay feedIn and feedInCost on all export. Saldering ends 2027-01-01: add a tariff row from that date with `netMetering: false`. `energy.overview` `house` adds `selfConsumedKwh`, `nettedKwh`, `netImportKwh`, `netExportKwh`, `selfConsumptionPct`, `coverageDirectPct`, `coverageNettedPct`, `feedInEur`, `feedInCostEur` and `netMetering` (the current tariff's flag); all null when no month counts. The one-off setup uses `rooms.ensure`, `items.create` and `items.addRelation` (`powers`); the collectors find their meters with `items.listAll`.
- `inbox.importGeojson` of a room that already exists is a rescan: it merges by `scan_kind` (moves matched Things, adds new ones, flags the rest with `scan.missing_at`) and never duplicates; it returns `{ ok, roomId, created, matched, moved, missing }`. A capture that is already `processed` is refused with BAD_REQUEST. `homebase-scan/1` (FeatureCollection `format` / `properties.format`, or any feature `properties.featureType`) is room-frame metres: `room` polygons are the floor outline (not furniture), `wall` LineStrings are walls, `opening` LineStrings are door/window/opening segments, `object` polygons are furniture with optional dims, `photo` Points are ignored for the plan. A file with no `featureType` is the old MappedIn lon/lat export and is unchanged.
- Room scans (Workbench): `inbox.importGeojson` and `rooms.upsertFromScan` each record a `room_scans` row in their transaction: the room's geometry before (null when the scan created the room) and after, and every Thing change (`matched`, `moved`, `created`, `missing`, with position and touched attribute keys before and after). `rooms.scans({ roomId })` lists a room's scans newest first with counts; `rooms.scanDiff({ scanId })` returns one scan's before/after geometry and changes with Thing names (`(deleted)` for a Thing that is gone); `rooms.revertScan({ scanId })` undoes the room's newest non-reverted scan only (CONFLICT otherwise): geometry, source, floor, positions and missing flags come back, the scan's capture goes back to `pending` so it can be imported again, and Things it created are deleted unless they were confirmed or rejected, decided, edited by a user since the scan, or have photos, pins, relations, links, tasks, ideas or children; it returns `{ restored, deleted, kept }`. Rows are never deleted, also not when their room is removed. A rejected Thing still takes part in a rescan's matching: the polygon it matches is left alone (no move, no new Thing, never flagged missing).
- Room pins (Workbench only): `pins.listForRoom({ roomId })` → every pin on the Photos of the room and of the rooms cut from it (recursively; not house-scoped), ordered by photoId then pin id: the pin row plus `photoTitle`, `photoStorageKey`, `itemName`, `itemAreaColor` and `item: { id, name, role, type, tags, decision, verificationStatus, status, areaId, attributes: { hostname?, ip?, os?, ram_gb?, storage_gb?, cpu?, brand? } } | null` (`type` = `attributes.type`, else `role`; `tags` = `attributes.tags` plus `brand`, lower case). Dismissed pins and pins of archived or rejected Things are left out; item-less pins carry `item: null`.
- Photo Place (Workbench only): `photos.setRoom({ id, roomId | null })` changes a Photo's own room only (pins and its Thing's room stay); a new room clears its camera, the same room writes nothing; NOT_FOUND for an unknown photo, BAD_REQUEST for an unknown room or a room outside its Thing's house; logs `photo.moved` on the photo; returns `{ id, roomId, cameraCleared }`. `photos.listAll` rows carry `photoRoomId` (the photo's own room; `roomId` there is its Thing's room first). `inbox.list` image rows carry optional `photoId`, `photoRoomId`, `roomName`, `houseId`, `houseName` and `hasCamera` from that location Photo (null when none) so Inbox can set or move the Place. `houseId` is the photo's room's house, else the capture's own `captures.houseId` (stamped from `x-house-id` on `inbox.create`, or set later). Optional list input `{ houseId, includeUnknown, view: "open" | "dismissed" | "all" }` — omitted (Flow / iOS) still returns every status. Workbench-only writes: `inbox.assignPlace({ ids, houseId?, roomId? })` (room wins and sets the house; house alone leaves the Place), `inbox.restore({ ids })` (dismissed → pending), `inbox.dismissMany({ ids })`. Each logs a capture event.
- Work queue (Workbench first; Flow and iOS may switch at their own pace, their local rules keep working): tRPC `items.queue({ houseId?, roomId?, lens?: "lab" })` → `{ toSort, toCheck, toPlace, toDecide, toTopic, lens: { needsRole, needsBackup } | null, laterDays, counts }` (id lists; `toSort` are pending capture ids oldest first, the rest item ids), computed in `api/lib/queue.ts` with the same rules as `src/flow/data.ts` and `src/flow/lenses.ts`: check = active + detected; place = active, real, not to check, no room; decide = same, no decision or a `later` older than `LATER_DAYS` (7); topic = same, still in the default Topic `things` (the Topic inbox: a Thing that arrived without a Topic waits here until someone picks one; `counts.toTopic`). `items.suggestTopic({ id })` (Workbench only, 2026-11-09) proposes one: `{ areaId, slug, name, reason, source: "rule" | "ai" } | null` from `api/lib/suggestTopic.ts` — `role`/`type` first, then the head noun of the name (Dutch compounds: "laptoptas" → containers), else `claude -p` (the Claude Code CLI, like `pins.labelWithClaude`; never the API provider from Settings) choosing among existing Topics; null when nothing fits, PRECONDITION_FAILED with the CLI's message when `claude` is missing, not signed in or answers badly; NOT_FOUND for an unknown Thing. It never writes and never proposes `things`; the screen applies it with `items.update`; a capture belongs to its location Photo's room's house, else its own `houseId`, and a capture with no house counts in every house. `houseId` defaults to the session house (null = all).
- Importers and collectors that create items (scripts, not people) pass `items.create({ ..., suggestLinks: false })`: no name-based suggestions, no LLM call and no `links-suggested` event. Without the field (the Workbench and Flow) it defaults to true.
- Default topic: `areaId` is optional in `items.create`, `inbox.fileObject` and `inbox.acceptMany` items. A new Thing without one goes to the topic with slug `things` (name "Things"), created in the current database on first need; filing onto an existing Thing needs no topic. Callers that send `areaId` see no change.
- Location:
  - A place is a room: Flow's `Place = { roomId }`. Items, captures and photos locate by `roomId`; the room carries its house and floor.
  - The `x-house-id` header is the session house. Without the header (null), lists cover all houses; `rooms.ensure` and `rooms.create` require a house.
  - `items.update`, `items.create`, `inbox.acceptMany` and `inbox.fileObject` take `roomId` (and `houseId` for an unplaced item); the old `floor`/`room` inputs are ignored by validation, not rejected.
  - `items.update` with `houseId` and no `roomId` moves an item, unplaced, into another house; for its own house it changes nothing.
- Data meaning:
  - `items.decision` is `keep`, `sell`, `donate`, `toss` or `later`. `items.decidedAt` is the time of the decision.
  - "Gone" is `items.status = "archived"` on an item with a decision. Do not add a second status for this.
  - `items.verificationStatus` is `detected`, `confirmed` or `rejected`. Flow never shows `rejected` items.
  - `items.attributes` has two kinds of keys. Plain keys describe the thing: `role`, `brand`, `model`, `serial`, `os`, `cpu`, `ram_gb`, `storage_gb`, `hostname`, `ip`, `mac`, and for machines also `uuid` (hardware UUID), `macs` (every network card, comma list) and `aliases` (other names, comma list; the collectors match on them). `serial`, `mac` and `machine.id` identify a machine; hostnames and IPs are derived from the register, not typed. Prefixed keys hold workflow state: `sell.ask_price`, `sell.channel`, `sell.listed_at`, `sell.sold_price`, `sell.sold_at`, `donate.to`, `lab.exclude`, `lab.backup`, `lab.data_copied_at`, `lab.wiped_at`, `storage.starred`, `storage.hidden`, `storage.disk`, `machine.id`. Do not rename these keys. Dates are `YYYY-MM-DD`; prices are whole euros. `storage.starred` / `storage.hidden` are `yes` on a machine (role laptop/desktop/server/sbc/nas); `machine.id` is the preferred tracker hostname / IP / MAC: Storage pins starred machines first and hides the rest from the default list (Show hidden reveals them). View-only — they do not archive the Thing or its volumes. `storage.disk` on a disk Thing (role `storage`) is the kernel disk name (`sda`, `disk9`) that computer-attached volumes with that `device` should draw on when auto-match is ambiguous.
  - `type` (plain key) is the Thing's most specific Type from the tree in `db/taxonomy.ts` (`TYPE_TREE`: e.g. `imac` under `desktop` under `computer`; a NAS is a `computer`). Store only the most specific node; ancestors are derived from the tree, never stored. Without `type` the Type comes from `role` (`derivedType`). `role` is unchanged, and `kind` stays the service-runtime key the Systems view uses (node, docker, systemd, launchd): it is not a Type. Triage keeps `type` only for tree keys (`isTypeNode`, lower-cased); free text from the model is dropped.
  - `tags` (plain key) is a comma-separated, lower-case list (`apple,home-lab`); `brand` counts as a tag too (`tagsOf`). Whether a Thing is a computer is one rule, `judgeComputer` / `isMachineItem` in `db/taxonomy.ts`, shared by Systems, the Workbench and scripts.
  - A relation of type `backs-up` means `fromItemId` (a NAS, drive or server) holds the backup of `toItemId` (the device).
  - Energy meters: role `meter` (a Plugwise plug, the DSMR grid meter or the solar inverter). Plain keys: `meter_kind` (`plug`, `grid`, `solar`), `mac` (a plug's circle MAC), `solaredge_site` (the inverter's SolarEdge site id). Monthly figures live in `energy_months`, not in attributes.
  - A relation of type `powers` means `fromItemId` (a plug) powers `toItemId` (an appliance). An appliance shows its plug's whole use; a shared plug's use is never split.
  - A relation of type `attached-to` means `fromItemId` (an external drive or NAS) is plugged into or mounted on `toItemId` (a computer); the Storage page groups it under that computer. It does not make the drive internal.
  - The Computer Lab adds these keys. Plain: `drive_type` (`hdd`, `ssd`, `nvme`, `sd`, `usb`, `emmc`), `storage_free_gb`, `mount_point`. Workflow: `lab.ref` (the old lab app's id or ids, comma-separated; marks an imported item), `lab.status` (`Inactive`, `Storage`, `Broken`), `lab.notes`, `lab.category`, `lab.merged_into`, and `backup.<targetItemId>.last_at` / `.verified_at` / `.current` / `.notes` on the backed-up device. Do not rename them.
  - A photo's `camera` is where it was taken in its room frame: `xM, yM, headingDeg (0 = +x, counter-clockwise), fovDeg, heightM`; cutouts have none.
  - An internal drive is an item with role `storage` whose `parentId` is its computer. It needs no backup of its own while it sits in the computer.
  - A Thing that a floor scan created carries the plain key `scan_kind` (the exporter's polygon kind, e.g. `stove`). Do not rename it: a rescan matches by it. Only a scan sets it (`inbox.importGeojson`, `rooms.upsertFromScan`); a script or agent that registers Things from photos or text must not invent a value (`wes-scan-object` was cleared on 2026-11-08, `scripts/clear-scan-kind-2026-11.mjs`). A hand-registered Thing has no `scan_kind`, so a rescan never flags it missing; `scan_slug` may record where it came from.
  - The workflow key `scan.missing_at` (`YYYY-MM-DD`) is set when the latest scan of the Thing's room did not detect it, and removed when a later scan does. A missing Thing keeps its position, room and verification.
  - A Thing's 3D model lives on `items.model3dRoute` (`auto` / `none` / `agent` / `meshy` / `capture`, default `auto`) and `items.model3dUrl` (nullable `/uploads/…` or an http(s) `.glb` / `.usdz` / `.js`). `auto` is resolved at read time: `attributes.favourite` or `favorite` of `yes` / `true` / `1` → Object Capture, else Meshy. `items.listAll` and `items.get` add `effectiveModel3dRoute`. Writes go through `items.setModel3d`. Never delete a Thing to clear a model.

## 3. Database

- Live database: MySQL on `10.50.0.10`, database `declutter` (`DATABASE_URL`).
- Test database: `declutter_test` (`TEST_DATABASE_URL`). It is disposable. The tests in `api/test/` truncate it.
- Change the schema only in `db/schema.ts`. Then run `npm run db:generate -- --name <short-name>`. Read the generated SQL. Commit the SQL, the snapshot and `meta/_journal.json`.
- Make one schema change branch at a time. Two branches must not use the same migration number.
- Additive changes (new table, new nullable column, new index): apply to the test database, then to the live database. Then tell Rick.
- Destructive changes (drop, rename, type change, backfill): ask Rick first. Make a backup first.
- Do not change the live database by hand. Do not point tests or experiments at `DATABASE_URL`.

CAUTION: Both databases use the same `uploads/` folder. Delete code removes a file when no row in the *current* database uses it. Do not copy live rows into `declutter_test`, or a test delete can remove a live photo.

## 4. Git

- Run `git fetch` before you start.
- Work in your own worktree: `git worktree add ../declutter-<topic> -b <topic> origin/main`. Do not switch branches in a folder that another session uses.
- Use one topic for each branch.

  1. Run `npm run check`. It must pass. Both front ends share the API types.
  2. Run `npm test` when you change database code.
  3. Run `npm run build` when you change the build or the server.

## 5. Product words

- Use five words on every screen: Thing, Place, Photo, Decision, Lens.
- Topic, Type and Kind are three different things; do not mix them up (decided 2026-11-07):
  - **Topic** is the screen name for an `areas` row (`items.areaId`, tRPC `areas.*`, URL `/areas/:slug`). It is the flat, required browsing bucket (Computers, Furniture, Things, …) with a colour, an icon and optional `attributeDefs`. Code and routes keep `area`; screens say Topic, never "Kind", "Category" or "Area".
  - **Type** is `attributes.type`, a node of `TYPE_TREE` in `db/taxonomy.ts`; it says precisely what the Thing is and is hierarchical (`imac` → `desktop` → `computer`). Without it `role` decides (`derivedType`).
  - **Kind** is not a Thing classification: `attributes.kind` is the service runtime in Systems (node, docker, launchd), `scan_kind` the scanner's polygon kind, and homebase-3d's `category` the RoomPlan category. None of these is shown as a Thing's Topic or Type.
- The Flow loop is "register all, act later": Snap, then Sort (what is it, is it right, where is it), then Act (keep, sell, donate, toss, later), then Gone.
- A lens adds its own fields, views and steps for one field of work (first lens: Computer lab). A lens does not copy core data and does not use a second database.
- Live meter data (DSMR, Home Assistant, Zigbee) is read-only. It does not go through the confirm step.
