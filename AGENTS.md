# Rules for agents in this repo

Read this before you change code. These rules apply to every agent (Kimi, Claude sessions, others) and to Rick's own scripts. Rick decides when a rule changes.

## 1. Who owns what

| Area | Files | Owner |
| --- | --- | --- |
| Flow front end | `flow/`, `src/flow/` | Claude session "declutter-flow" |
| Workbench front end | `index.html`, `src/pages/`, `src/components/`, `src/context/` | Rick, or the session Rick assigns |
| API and database | `api/`, `db/` | Shared: follow sections 2, 3 and 4 |

- Do not edit `flow/` or `src/flow/`. If your change needs a Flow change, stop and tell Rick.
- If `npm run check` shows errors only under `src/flow/`, your change broke a Flow contract. Do not fix Flow yourself. Tell Rick.
- Do not commit files that another session made (for example its plans in `docs/`).
- On 2026-10-03 one session (finalize plan) worked on every area; the ownership above applies again to new work.

- Storage collectors (`scripts/storage-report-local.mjs` for the machine it runs on; the Data Tracker for the others): tRPC `storage.report({ itemId, source, volumes: [{ mountPoint, label?, fsType?, device?, container?, capacityBytes, usedBytes, dirs?: [{ path, bytes }] }] })`, bytes, at most 64 volumes and 100 directories per volume, only for an item whose `role` is `laptop`, `desktop`, `server`, `sbc`, `nas` or `storage`. A report never changes a volume's `dataRole` and never deletes a volume; `container` (at most 64, e.g. the APFS container `disk3`) groups volumes that share one container's capacity: they must report the same `capacityBytes`, their summed `usedBytes` must fit in it, and the device counts that capacity once per container; null or absent = the volume is its own container (old payloads keep working). It keeps the device's `storage_gb` equal to the sum of its container capacities and `storage_free_gb` to that minus every volume's use. The whole report is refused with BAD_REQUEST when any volume has used above capacity, the item is archived, or a length limit is exceeded: mountPoint 255, label 128, device 128, path 512, source 32. For the Data Tracker: one volume per filesystem: drop bind/overlay duplicates of the same device or the device's storage_gb double-counts; at most 64 volumes per report. Reads: `storage.overview` (totals count only volumes of active items: used bytes per data role, plus one `freeBytes` and `capacityBytes` figure; capacity belongs to no role; computers carry `attached`, devices `attachedRelationId` and `backsUp`), `storage.dirs`; writes: the role is set with `storage.setRole({ volumeId, dataRole })`, one of `unique`, `test`, `backup`, `archive`, `system`, `media`, `scratch` or `null`; `storage.removeVolume({ volumeId })` deletes a volume and its directories and recomputes `storage_gb`/`storage_free_gb` from the remaining volumes (with none left the keys stay). `storage_gb`/`storage_free_gb` are decimal GB (bytes / 1e9), so a hand-entered GiB value moves once at the first report.
- Services collectors (`scripts/services-report-local.mjs` / `.ts` on the machine it runs on, dry unless `--apply`, PATH includes `~/.orbstack/bin`; `scripts/services-report-fleet.ts` reads a fleet snapshot such as `http://10.50.0.10/claudemux-fleet.html` and matches hostname exactly, then IP exactly; `scripts/services-report-proxmox.ts --ssh root@10.50.0.155` reads `pvesh get /cluster/resources` plus per-guest `pvesh get /nodes/<node>/qemu|lxc/<vmid>/config`, or `pct list`+`qm list`, matches hostname `pve` / IP `10.50.0.155` / name containing proxmox; `scripts/services-report-projects.ts` reads `http://10.50.0.10/projects/`): tRPC `services.report({ itemId, source, merge?, containers?: [{ name, status?, image?, port?, ports?, url?, size?, imageSize?, layers?, created?, mounts?: [{ source, dest, type?, size? }] }], node?: [{ name, status?, port?, url? }], web?: [{ label, url?, port?, urls?, ports?, status? }], vms?: [{ vmid, name, status?, memMb?, diskGb?, usedGb?, template?, disks?: [{ name, sizeGb?, storage? }], mounts? }], lxc?: [{ vmid, name, status?, memMb?, diskGb?, usedGb?, template?, disks?, mounts? }], databases?: [{ name, engine?, status?, port?, size?, url?, target?, detail?, checked? }], projects?: [{ name, kind?, status?, tokens?, size?, updatedAt?, minutes?, url?, path? }] })`, at most 200 containers/projects, 100 node/web/vms/lxc/databases rows, name/label at most 64 (project name 128, path/target 255), source at most 32, only for an item whose `role` is `laptop`, `desktop`, `server`, `sbc` or `nas`. Fleet HTML groups service rows by base label (strip `:port` and a duplicate `project/` prefix) into one `web` row with `ports` / `urls` and status `ok` if any row is ok, otherwise the worst; nameless listeners like `port:18790` stay as-is and are listed last. Fleet maps `class="mtx databases-table"` by header text (`kind`→engine, `label`→name, plus target/status/detail/checked), skips the header/`th` row, and uniques by kind+label+target. Other `mtx` tables stay stripped except `services-table` and directory-like project tables. It does not lift web labels into `projects`. A per-host directory table (`class="directory"` / `pd-k` directory / header directory|path|project with path-like cells) is imported as `projects` (`path` + basename `name`, `kind` from the row, else `unknown`); a project/directory-looking table that yields no rows is listed in `skippedProjectTables` with a reason (never silent). Container `table.projects` pd-rows stay containers and are not skip-listed. `matchMachine` also reads item attributes `host_alias` (LAN Police short name, comma list allowed) and `aliases`, and strips `.local` / case on hostnames. The `/projects/` collector merges Claude Code rows (tokens, project size, last activity) onto the same `projects` key; same machine + same path is one entry (prefer tokens / newer updatedAt / a known kind). Both collectors' dry runs print `byKind` counts per machine. Local Docker maps `(unhealthy)` to status `warn` and publishes the host port; it also writes size / imageSize / layers / created / mounts when inspect/`df -v` are available. Proxmox writes QEMU sata/ide/scsi/virtio/efidisk/tpmstate sizes and storage (including 4M EFI/TPM), LXC rootfs + mpN mounts and maxmem. Config-read failures log to stderr; the collector exits non-zero if every guest config fails. Each sent list replaces that attribute unless `merge` (then upsert by name / label / vmid / engine+name+target / path; empty + merge leaves the key); omitted lists stay. The whole report is refused with BAD_REQUEST when the item is missing, archived, not a machine, or no list key is sent. Writes one `services.report` event. The Systems view reads these attributes (and child Things with role container/docker) and does not fetch the fleet HTML, `/projects/` or SSH to Proxmox. VMs, LXC, databases and projects are their own leaf kinds (stopped dimmed, templates fainter; project active = green, older/stale fade).
- Energy collectors (`~/plugwise/report_energy_homebase.py` and `~/plugwise/report_house_energy.py` on dockermac-1): tRPC `energy.report({ itemId, source, months: [{ month: "YYYY-MM", kwhNormal?, kwhOffpeak?, kwhReturnedNormal?, kwhReturnedOffpeak?, kwhProduced?, avgW?, baseW?, peakW?, hours? }] })`, 1–200 months, source at most 32 characters, every number non-negative and finite, a month never after the current one (local time) and never twice in one report. Fields follow the item's `meter_kind`: `plug` needs kwhNormal/kwhOffpeak and may send avgW/baseW/peakW/hours; `grid` needs kwhNormal/kwhOffpeak (DSMR T2/T1) and kwhReturnedNormal/kwhReturnedOffpeak, and may send hours; `solar` needs kwhProduced and may send hours. The whole report is refused with BAD_REQUEST when the item is missing, archived, not role `meter` or has no known `meter_kind`, when a required field is missing, a field does not belong to the kind, or a value is above its column's maximum. It upserts by (itemId, month) in one transaction, never deletes, and writes no item event (31 meters report nightly; these are measurements, not edits). Reads: `energy.overview` (last 12 complete months; scoped like storage.overview), `energy.forItem` (a plug, or an item a plug powers; `plug: null` for anything else). Writes by Rick: `energy.setTariff` (logs an event; optional `netMetering`, default true). Net metering (saldering, Energiek): a tariff row's `netMetering` flag decides per month; over the window's netMetering months import and export net as a whole (saldering is yearly), the netted kWh cost the average import price, terugleverkosten (`feedInCost`) apply to all exported kWh and terugleververgoeding (`feedIn`) only to the surplus above import; months without netMetering pay feedIn and feedInCost on all export. Saldering ends 2027-01-01: add a tariff row from that date with `netMetering: false`. `energy.overview` `house` adds `selfConsumedKwh`, `nettedKwh`, `netImportKwh`, `netExportKwh`, `selfConsumptionPct`, `coverageDirectPct`, `coverageNettedPct`, `feedInEur`, `feedInCostEur` and `netMetering` (the current tariff's flag); all null when no month counts. The one-off setup uses `rooms.ensure`, `items.create` and `items.addRelation` (`powers`); the collectors find their meters with `items.listAll`.
- `inbox.importGeojson` of a room that already exists is a rescan: it merges by `scan_kind` (moves matched Things, adds new ones, flags the rest with `scan.missing_at`) and never duplicates; it returns `{ ok, roomId, created, matched, moved, missing }`. A capture that is already `processed` is refused with BAD_REQUEST.
- Room scans (Workbench): `inbox.importGeojson` and `rooms.upsertFromScan` each record a `room_scans` row in their transaction: the room's geometry before (null when the scan created the room) and after, and every Thing change (`matched`, `moved`, `created`, `missing`, with position and touched attribute keys before and after). `rooms.scans({ roomId })` lists a room's scans newest first with counts; `rooms.scanDiff({ scanId })` returns one scan's before/after geometry and changes with Thing names (`(deleted)` for a Thing that is gone); `rooms.revertScan({ scanId })` undoes the room's newest non-reverted scan only (CONFLICT otherwise): geometry, source, floor, positions and missing flags come back, the scan's capture goes back to `pending` so it can be imported again, and Things it created are deleted unless they were confirmed or rejected, decided, edited by a user since the scan, or have photos, pins, relations, links, tasks, ideas or children; it returns `{ restored, deleted, kept }`. Rows are never deleted, also not when their room is removed. A rejected Thing still takes part in a rescan's matching: the polygon it matches is left alone (no move, no new Thing, never flagged missing).
- Photo Place (Workbench only): `photos.setRoom({ id, roomId | null })` changes a Photo's own room only (pins and its Thing's room stay); a new room clears its camera, the same room writes nothing; NOT_FOUND for an unknown photo, BAD_REQUEST for an unknown room or a room outside its Thing's house; logs `photo.moved` on the photo; returns `{ id, roomId, cameraCleared }`. `photos.listAll` rows carry `photoRoomId` (the photo's own room; `roomId` there is its Thing's room first).
- Importers and collectors that create items (scripts, not people) pass `items.create({ ..., suggestLinks: false })`: no name-based suggestions, no LLM call and no `links-suggested` event. Without the field (the Workbench and Flow) it defaults to true.
- Location:
  - A place is a room: Flow's `Place = { roomId }`. Items, captures and photos locate by `roomId`; the room carries its house and floor.
  - The `x-house-id` header is the session house. Without the header (null), lists cover all houses; `rooms.ensure` and `rooms.create` require a house.
  - `items.update`, `items.create`, `inbox.acceptMany` and `inbox.fileObject` take `roomId` (and `houseId` for an unplaced item); the old `floor`/`room` inputs are ignored by validation, not rejected.
  - `items.update` with `houseId` and no `roomId` moves an item, unplaced, into another house; for its own house it changes nothing.
- Data meaning:
  - `items.decision` is `keep`, `sell`, `donate`, `toss` or `later`. `items.decidedAt` is the time of the decision.
  - "Gone" is `items.status = "archived"` on an item with a decision. Do not add a second status for this.
  - `items.verificationStatus` is `detected`, `confirmed` or `rejected`. Flow never shows `rejected` items.
  - `items.attributes` has two kinds of keys. Plain keys describe the thing: `role`, `brand`, `model`, `serial`, `os`, `cpu`, `ram_gb`, `storage_gb`, `hostname`, `ip`, `mac`. Prefixed keys hold workflow state: `sell.ask_price`, `sell.channel`, `sell.listed_at`, `sell.sold_price`, `sell.sold_at`, `donate.to`, `lab.exclude`, `lab.backup`, `lab.data_copied_at`, `lab.wiped_at`. Do not rename these keys. Dates are `YYYY-MM-DD`; prices are whole euros.
  - A relation of type `backs-up` means `fromItemId` (a NAS, drive or server) holds the backup of `toItemId` (the device).
  - Energy meters: role `meter` (a Plugwise plug, the DSMR grid meter or the solar inverter). Plain keys: `meter_kind` (`plug`, `grid`, `solar`), `mac` (a plug's circle MAC), `solaredge_site` (the inverter's SolarEdge site id). Monthly figures live in `energy_months`, not in attributes.
  - A relation of type `powers` means `fromItemId` (a plug) powers `toItemId` (an appliance). An appliance shows its plug's whole use; a shared plug's use is never split.
  - A relation of type `attached-to` means `fromItemId` (an external drive or NAS) is plugged into or mounted on `toItemId` (a computer); the Storage page groups it under that computer. It does not make the drive internal.
  - The Computer Lab adds these keys. Plain: `drive_type` (`hdd`, `ssd`, `nvme`, `sd`, `usb`, `emmc`), `storage_free_gb`, `mount_point`. Workflow: `lab.ref` (the old lab app's id or ids, comma-separated; marks an imported item), `lab.status` (`Inactive`, `Storage`, `Broken`), `lab.notes`, `lab.category`, `lab.merged_into`, and `backup.<targetItemId>.last_at` / `.verified_at` / `.current` / `.notes` on the backed-up device. Do not rename them.
  - A photo's `camera` is where it was taken in its room frame: `xM, yM, headingDeg (0 = +x, counter-clockwise), fovDeg, heightM`; cutouts have none.
  - An internal drive is an item with role `storage` whose `parentId` is its computer. It needs no backup of its own while it sits in the computer.
  - A Thing that a floor scan created carries the plain key `scan_kind` (the exporter's polygon kind, e.g. `stove`). Do not rename it: a rescan matches by it.
  - The workflow key `scan.missing_at` (`YYYY-MM-DD`) is set when the latest scan of the Thing's room did not detect it, and removed when a later scan does. A missing Thing keeps its position, room and verification.

## 3. Database

- Live database: MySQL on `10.50.0.10`, database `declutter` (`DATABASE_URL`).
- Test database: `declutter_test` (`TEST_DATABASE_URL`). It is disposable. The tests in `api/test/` truncate it.
- Change the schema only in `db/schema.ts`. Then run `npm run db:generate -- --name <short-name>`. Read the generated SQL. Commit the SQL, the snapshot and `meta/_journal.json`.
- Make one schema change branch at a time. Two branches must not use the same migration number.
- Additive changes (new table, new nullable column, new index): apply to the test database, then to the live database. Then tell Rick.
- Destructive changes (drop, rename, type change, backfill): ask Rick first. Make a backup first.
- Do not change the live database by hand. Do not point tests or experiments at `DATABASE_URL`.

CAUTION: Both databases use the same `uploads/` folder. Delete code removes a file when no row in the *current* database uses it. Do not copy live rows into `declutter_test`, or a test delete can remove a live photo.

## 4. Git

- Run `git fetch` before you start.
- Work in your own worktree: `git worktree add ../declutter-<topic> -b <topic> origin/main`. Do not switch branches in a folder that another session uses.
- Use one topic for each branch.
- Before you push:
  1. Run `npm run check`. It must pass. Both front ends share the API types.
  2. Run `npm test` when you change database code.
  3. Run `npm run build` when you change the build or the server.
- Merge to `main` only when Rick says so. Use a fast-forward or a rebase. Do not force-push to `main`.
- Write in the commit message why you made the change, not only what you changed.

## 5. Product words

- Use five words on every screen: Thing, Place, Photo, Decision, Lens.
- The Flow loop is "register all, act later": Snap, then Sort (what is it, is it right, where is it), then Act (keep, sell, donate, toss, later), then Gone.
- A lens adds its own fields, views and steps for one field of work (first lens: Computer lab). A lens does not copy core data and does not use a second database.
- Live meter data (DSMR, Home Assistant, Zigbee) is read-only. It does not go through the confirm step.

## 6. Run the app

- `npm run dev` starts the Workbench at `/` and Flow at `/flow/` on port 3000. Production runs `node dist/boot.js` on port 3001 from `/Volumes/T7/declutter`.
- Run one dev server for each worktree, on another port and against the test database: `DATABASE_URL="$TEST_URL" npx vite --port 3002`. `node scripts/seed-test-db.mjs` fills the test database with a two-house sample.
